# Privacy Policy

`anilist-mcp-server` is a local [Model Context Protocol](https://modelcontextprotocol.io)
server: it runs as a process on your own machine (via `npx` or a local clone),
speaking stdio to your MCP client (Claude Desktop, Claude Code, etc.). It has
no backend of its own, and no telemetry or analytics. This policy describes
everything it does with your data.

**Read this first if you're only skimming:** unlike a read-only data server,
this one can act on your real AniList account when you (or the AI model acting
for you) ask it to. See
[Usage and third-party sharing](#usage-and-third-party-sharing) below for the
full list of what it can change.

## Data collection

`anilist-mcp-server` collects no data of its own. It has no database and no
accounts, and it sends nothing to its maintainer or to any analytics or
telemetry service.

The only inputs it handles are:

- **Credentials you supply**, via environment variables in your MCP client's
  own config (e.g. `claude_desktop_config.json`): `ANILIST_CLIENT_ID` /
  `ANILIST_CLIENT_SECRET` (your own registered AniList app, needed to start a
  login), and either an `ANILIST_ACCESS_TOKEN` you pre-supply or the access
  token from running the `login_anilist` tool. All are optional: the server
  starts and every read-only tool works with no credentials at all. These
  stay in your client's local config file (or, for a token from
  `login_anilist`, on local disk, see
  [Storage and retention](#storage-and-retention)); `anilist-mcp-server` never
  transmits them anywhere except as described below.
- **Tool call arguments**, generated by the AI model you're using (e.g. an
  anime/manga title, a username, a list entry's status/score/progress, the
  text of an activity post or forum comment) as it calls one of this server's
  tools on your behalf.

## Usage and third-party sharing

Every tool call makes one outbound HTTPS request, to AniList's own
infrastructure: the public GraphQL API (`graphql.anilist.co`) for every tool,
plus AniList's OAuth endpoints (`anilist.co/api/v2/oauth/*`) only during the
one-time `login_anilist` / `submit_anilist_redirect` login flow. No other
third party is ever contacted.

- **Reads** (search, details, genres/tags, recommendations, forum threads,
  activity feeds, public/unlisted user profiles and lists) call the public
  GraphQL endpoint with no credentials and touch only public data.
- **Your access token, when configured**, rides on every GraphQL request that
  needs it, as a standard `Authorization: Bearer <token>` header. To AniList
  the request looks the same as one you'd make while logged in.
- **This server can write to and post from your real AniList account** when a
  personal/mutation tool runs with a valid token. That's the main thing
  setting it apart from a read-only MCP server. These tools write to
  `graphql.anilist.co` when called, with no confirmation step of the server's
  own:
  - **Your list**: `add_list_entry`, `update_list_entry`, `remove_list_entry`
    add, change (status, score, progress, notes, dates, custom lists,
    advanced scores, rewatches), or delete entries on your anime/manga list.
  - **Favourites and follows**: `toggle_favourite` (anime, manga, characters,
    staff, or studios) and `toggle_follow_user`.
  - **Public posts under your name**: `post_text_activity`,
    `post_message_activity`, `post_thread`, `post_thread_comment` publish to
    AniList's public activity feed or forums, visible to other users under
    your name, the same as posting on anilist.co. The `delete_activity`,
    `delete_thread`, and `delete_thread_comment` counterparts take those
    posts back down.
  - **Account settings**: `update_user` changes settings on your AniList
    profile.

  Each of these needs a valid access token (`ANILIST_ACCESS_TOKEN` or one from
  `login_anilist`); without one it returns an error rather than trying the
  request anyway. That token is the only gate, so if the model calls one of
  these tools while it's configured, the write happens. Check what your agent
  intends before you hand it a write-capable token, the same care you'd take
  with any tool that can touch a real account.

- **`get_notifications` / `get_authorized_user`** read private data (your own
  notifications, your own profile as seen while logged in) using the same
  bearer token. `get_authorized_user` doesn't write anything; `get_notifications`
  is read-only by default too, but its opt-in `markAsRead: true` resets your
  unread-notification badge count as a side effect.
- **The login flow** (`login_anilist`) opens your system browser to AniList's
  own authorize page, where you sign in and approve with AniList directly
  (this server never sees your AniList password). AniList redirects back with
  a one-time code, which the server trades for an access token at AniList's
  token endpoint, sending your `ANILIST_CLIENT_ID`/`ANILIST_CLIENT_SECRET` and
  that code but never a password.

Once a request reaches AniList, it falls under
[AniList's own Terms & Privacy](https://anilist.co/terms) (AniList publishes
one combined page, not a separate privacy policy). `anilist-mcp-server` sends
data nowhere else: no analytics or logging service, and no server run by its
maintainer.

## Storage and retention

- **Caching**: successful **read** responses are cached in the server
  process's own memory only (never written to disk), for a short configurable
  TTL (`CACHE_TTL_MS`, default 5 minutes) to cut latency and ease pressure on
  AniList's rate-limited API. Cache keys include the token in use, so
  different accounts' cached data can never cross. Mutations are never cached,
  and a successful one immediately clears the whole cache (a write can change
  the answer to an already-cached read, e.g. a newly-favourited title's
  `isFavourite` flag), so the next read is fresh. The cache is cleared when
  the process exits and is never shared across machines or users.
- **Your access token**: if obtained via `login_anilist`, it is written to a
  single local file (`~/.config/anilist-mcp-server/tokens.json` on
  macOS/Linux, `%APPDATA%\anilist-mcp-server\tokens.json` on Windows, or the
  path in `ANILIST_TOKEN_STORE`), created with `0600` permissions
  (owner-read/write only) so it survives restarts without a fresh login
  (AniList tokens don't support refresh and last about a year). If you
  pre-supply `ANILIST_ACCESS_TOKEN` directly instead, it stays in memory for
  that run only and is **not** written to this file. Nothing about this token
  goes anywhere except to AniList itself, as described above.
- **Logging**: operational logs go to stderr only (never a file, never a
  remote endpoint), with credentials and tokens redacted before anything is
  written. `LOG_LEVEL` (default `info`) controls verbosity; the logs last
  only as long as your MCP client keeps that stderr stream around.
- Past the cache TTL, the on-disk token file, and the running process's
  lifetime, `anilist-mcp-server` keeps nothing. There is no other persistent
  storage, and once a request completes the server holds no copy of what you
  posted or wrote. AniList's own retention of that data (e.g. an activity post
  or list entry) falls under AniList's Terms & Privacy linked above.
