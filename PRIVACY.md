# Privacy Policy

`anilist-mcp-server` is a local [Model Context Protocol](https://modelcontextprotocol.io)
server: it runs as a process on your own machine (via `npx` or a local clone),
speaking stdio to your MCP client (Claude Desktop, Claude Code, etc.). It has
no server component of its own, no telemetry, and no analytics — this policy
covers exactly what it does with data, in full, because there isn't more to
say beyond it.

**Read this section first if you're only skimming:** unlike a read-only data
server, this one can act on your real AniList account when you (or the AI
model acting for you) ask it to — see
[Usage and third-party sharing](#usage-and-third-party-sharing) below for the
full list of what it can change.

## Data collection

`anilist-mcp-server` collects no data of its own. It has no database, no
accounts, and sends nothing to its maintainer or to any analytics/telemetry
service.

The only inputs it handles are:

- **Credentials you supply**, via environment variables in your MCP client's
  own config (e.g. `claude_desktop_config.json`): `ANILIST_CLIENT_ID` /
  `ANILIST_CLIENT_SECRET` (your own registered AniList app, needed to start a
  login), and either an `ANILIST_ACCESS_TOKEN` you pre-supply or the access
  token obtained by running the `login_anilist` tool. All are optional — the
  server starts and every read-only tool works with no credentials at all.
  These stay in your client's local config file (or, for a token obtained via
  `login_anilist`, on disk locally — see
  [Storage and retention](#storage-and-retention)); `anilist-mcp-server` never
  transmits them anywhere except as described below.
- **Tool call arguments**, generated by the AI model you're using (e.g. an
  anime/manga title, a username, a list entry's status/score/progress, the
  text of an activity post or forum comment) as it calls one of this server's
  tools on your behalf.

## Usage and third-party sharing

Every tool call results in an outbound HTTPS request to AniList's own
infrastructure — the public GraphQL API (`graphql.anilist.co`) for every
tool, plus AniList's OAuth endpoints (`anilist.co/api/v2/oauth/*`) only during
the one-time `login_anilist` / `submit_anilist_redirect` login flow. No other
third party is ever contacted.

- **Reads** (search, details, genres/tags, recommendations, forum threads,
  activity feeds, public/unlisted user profiles and lists) call the public
  GraphQL endpoint with no credentials and touch only public data.
- **Your access token, when configured**, is sent as an `Authorization:
Bearer <token>` HTTP header on every GraphQL request that needs it — this
  is standard OAuth bearer-token usage, not a custom scheme. AniList sees
  this exactly as if you'd made the request yourself while logged in.
- **This server can write to and post from your real AniList account** when
  a personal/mutation tool is called with a valid token. This is the single
  biggest difference from a purely read-only MCP server, and it is not
  hypothetical — the following tools perform real, live mutations against
  `graphql.anilist.co` the moment they're called, with no separate
  confirmation step of the server's own:
  - **Your list**: `add_list_entry`, `update_list_entry`, `remove_list_entry`
    — add, change (status, score, progress, notes, dates, custom lists,
    advanced scores, rewatches), or delete entries on your anime/manga list.
  - **Favourites and follows**: `toggle_favourite` (anime, manga, characters,
    staff, or studios) and `toggle_follow_user`.
  - **Public posts under your name**: `post_text_activity`,
    `post_message_activity`, `post_thread`, `post_thread_comment` — these
    publish content to AniList's public activity feed or forums, visible to
    other AniList users and attributed to your account, exactly as if you'd
    posted them yourself on anilist.co. Their `delete_activity`,
    `delete_thread`, `delete_thread_comment` counterparts remove your own
    posts the same way.
  - **Account settings**: `update_user` changes settings on your AniList
    profile.

  Every one of these requires a valid access token (`ANILIST_ACCESS_TOKEN` or
  one obtained via `login_anilist`); without one they return an error instead
  of a doomed request. There is no tool-level allow/deny list beyond that —
  if the calling AI model decides to invoke one of these tools with your
  token configured, the mutation happens. Review what your AI agent intends
  to do before authorizing it to act with a write-capable token, the same way
  you would before granting any other tool access to a real account.

- **`get_notifications` / `get_authorized_user`** read private data (your own
  notifications, your own profile as seen while logged in) using the same
  bearer token. `get_authorized_user` doesn't write anything; `get_notifications`
  is read-only by default too, but its opt-in `markAsRead: true` resets
  AniList's real unread-notification badge count as a side effect.
- **The login flow itself** (`login_anilist`): opens your system browser to
  AniList's own authorize page, where you sign in and approve directly with
  AniList (this server never sees your AniList password). AniList redirects
  back with a one-time code, which the server exchanges — sending your
  `ANILIST_CLIENT_ID`/`ANILIST_CLIENT_SECRET` and that code, never a
  password — for an access token at AniList's token endpoint.

Once a request reaches AniList, it is governed by
[AniList's own Terms & Privacy](https://anilist.co/terms) (AniList publishes
one combined page, not a separate privacy policy).
`anilist-mcp-server` sends data to no other destination — no analytics
vendor, no logging service, no server operated by its maintainer.

## Storage and retention

- **Caching**: successful **read** responses are cached in the server
  process's own memory only (never written to disk), for a short
  configurable TTL (`CACHE_TTL_MS`, default 5 minutes) to cut latency and
  ease pressure on AniList's rate-limited API. Cache keys include the actual
  token in use, so different accounts' cached data can never cross. Mutations
  are never cached, and a successful mutation immediately clears the entire
  cache (since a write can change the answer to previously-cached reads,
  e.g. a newly-favourited title's `isFavourite` flag) so the next read is
  guaranteed fresh. The cache is cleared entirely when the process exits and
  is never shared across machines or users.
- **Your access token**: if obtained via `login_anilist`, it is written to a
  single local file (`~/.config/anilist-mcp-server/tokens.json` on
  macOS/Linux, `%APPDATA%\anilist-mcp-server\tokens.json` on Windows, or the
  path in `ANILIST_TOKEN_STORE`), created with `0600` permissions
  (owner-read/write only) so it persists across restarts without requiring
  you to log in again — AniList tokens don't support refresh and are valid
  for about a year. If you instead pre-supply `ANILIST_ACCESS_TOKEN`
  directly, it is held in memory only for that run and is **not** written to
  this file. Nothing about this token is ever sent anywhere except to
  AniList itself, as described above.
- **Logging**: operational logs go to stderr only (never a file, never a
  remote endpoint), with credentials/tokens redacted before anything is
  written. Log verbosity is controlled by `LOG_LEVEL` (default `info`); logs
  live only as long as your MCP client keeps that stderr stream around.
- Beyond the cache TTL, the on-disk token file, and the running process's
  lifetime, `anilist-mcp-server` retains nothing. There is no other
  persistent storage layer, and no copy of anything you post or write is kept
  by the server itself once the request completes — AniList's own retention
  of that data (e.g. an activity post or list entry) is governed by AniList's
  Terms & Privacy linked above.
